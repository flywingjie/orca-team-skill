# 02 工作流与决策门

> 对应 `SPEC.md` §5。本文回答“一件事从立项到收尾怎么走”。

## 1. 七阶段总览

```text
① 立项（人）
   目标 / 范围 / 非目标 / 成功标准 / 拍板人

② 方案（规划层）
   规格草稿 → 契约定义 → 实现方案 → 测试与验收方案
   ↓ [规格门]：拍板人确认业务口径

③ 拆单（协调者）
   每张单 = 目标 + 改动 + 约束 + 归属 + 验收
   同时产出：波次、文件所有权、迁移号段、任务 × 模型分配表

④ 并行实施
   一任务一 worktree；同任务多 worker 共用工作区但文件分区
   worker 零 commit，交付补丁包

⑤ 收口
   合并实施分支 → 统一生成契约产物 → 全量门禁 → 冲突消解
   ↓ [设计门]：实现与契约产物一致

⑥ 验收
   verify（实跑门禁 + 用例）→ accept（条款级核验）
   ↓ [交付门]：拍板人签字

⑦ 回写
   进度 / 决策 / 遗留风险 / 下一步
```

## 1.1 三档口径：套多少流程

规范条目见 `SPEC.md` `S-4` / `S-5`。落地时按下表裁剪：

| 档 | 触发条件 | 必做 | 可省 | 谁签字 |
|---|---|---|---|---|
| **L0 轻** | 单会话可完成；无契约变更；变更面单一 | 一张五段式工单 + 定向验收证据 | DAG / 波次表 / 分配表 / 编排工具 / 决策门 | 人（看证据即可） |
| **L1 标** | 2–4 张工单；有依赖；契约已存在 | 工单 + 文件所有权表 + 任务×模型分配表 + 定向验证 | 编排工具（用子 agent 即可） | 人 |
| **L2 重** | 需定义/改动契约；需多实例并行；跨工具或需接管 | 全七阶段 + 三关 + 决策门 + Runbook | 无 | R-1 逐门放行 |

降档不等于减证据：**L0 也必须有工单五段式与实跑证据**（`SPEC.md` §1）。

## 1.2 难度只驱动四个旋钮，不驱动拆单

拆单按**结构接缝**（契约层 / 共享底座 / 同文件冲突 / 独立验收边界），**不看工作量**。
难度只调整下面四个旋钮：

| 旋钮 | 难度↑ 时的动作 |
|---|---|
| 角色 | 顾问/设计提前介入；补一次独立复核 |
| 模型 | 换更强推理模型（`SPEC.md` §8.1 能力矩阵） |
| 验收强度 | 定向验证 → 全量门禁 → 回归 |
| 并行度 | **不因难度下调**（并行度看接缝不看难度）；难度高反而要**拆得更细** |

最后一行是反直觉点：难度高 = 更多**窄而可独立验收**的单，不是更少更大的单。
「多文件」≠「多张单」；两张单绝不能碰同一文件。

## 2. 每个阶段的进入与退出条件

| 阶段 | 进入条件 | 退出条件 |
|---|---|---|
| ① 立项 | 需求已表达 | 目标、非目标、成功标准、拍板人明确 |
| ② 方案 | 立项完成 | 规格可验收；契约定义已冻结；待拍板项已列 |
| ③ 拆单 | 规格门通过 | 每张单五段齐全；依赖、所有权、号段、模型分配完毕 |
| ④ 实施 | 工单就绪 | 每个任务有补丁包 + 证据 + 回报三句 |
| ⑤ 收口 | 所有依赖任务结算 | 补丁已合入集成分支；契约产物已统一生成；全量门禁通过 |
| ⑥ 验收 | 设计门通过 | 条款级核验通过；遗留风险列明；交付门签字 |
| ⑦ 回写 | 验收通过 | 进度与决策已更新；工作区已处置 |

## 3. DAG 节点类型

| 节点 | 输入 | 输出 | 是否可并行 |
|---|---|---|---|
| `advisory` | 问题清单、既有文档 | 对照表、边界建议、异常清单 | 按域并行，但只读 |
| `spec` | 顾问产出、既有规格 | 规格草稿、待拍板清单 | 否 |
| `contract` | 规格 | 契约模型、错误码、权限映射 | 否（独占定义） |
| `backend` | 规格 + 契约 | 后端补丁包 | 与前端并行 |
| `frontend` | 规格 + 契约 | 前端补丁包 | 与后端并行 |
| `integration` | 各实施补丁 | 集成分支、契约产物、门禁结果 | 否（唯一写入方） |
| `verify` | 集成分支 | 用例结果、缺陷清单 | 否 |
| `accept` | 规格 + 验收结果 | 条款级核验表、风险清单 | 否 |

## 4. 决策门

### 4.1 三种门

| 门 | 问题 | 谁放行 | 未放行的后果 |
|---|---|---|---|
| **规格门** | 业务口径、范围、验收标准是否确认？ | 拍板人 | 不得进入契约与实施 |
| **设计门** | 实现与契约产物是否一致？门禁是否通过？ | 拍板人/授权人 | 不得验收、不得合并 |
| **交付门** | 条款是否满足？风险是否可接受？ | 拍板人 | 不得宣称完成、不得发布 |

### 4.2 门纪律

- 门是“暂停点”，不是“自动通过点”。
- agent 不得自行放行门；也不得用“先继续做，回头补签字”绕过。
- 门的结论必须落在文件里（决策记录或工单），不能只在对话里。
- 门被拒时必须写明：拒因、需改什么、改完由谁复核。

## 5. 波次规划

一个波次 = 依赖已全部结算、可以同时派发的一组任务。

计算步骤：

1. 列出所有未结算任务及其依赖。
2. 取依赖全部为“已结算”的任务。
3. 按文件所有权分组：需要改同一文件的任务**不得同波**。
4. 按模型家族分组：同波任务**不得重复模型家族**。
5. 并行度 ≤ 8；超过则按优先级切分。
6. 检查链深 ≤ 4；超过则考虑合并任务或拆分依赖。

工具：`scripts/plan.py` 可读取 TOML 并输出波次。

## 6. 收口的唯一写入方

- 契约**定义**：`contract` 单独占。
- 契约**产物**：`integration` 单独占（末波统一生成）。
- 共享文件（路由表、依赖清单、lockfile）：由 `integration` 单或专项单独占。

**规则**：任何任务发现需要改上述内容，必须回流对应 owner，不得“就地改一下”。

## 7. 基线

| 任务 | 基线 |
|---|---|
| 实施单 | 远端主分支（`origin/main` 或等价物） |
| 集成单 | 实施单的共同祖先或指定分支 |
| verify / accept | **集成分支**，不得基于某个实施分支 |

基线错误是隐蔽事故：worker 会基于旧代码开工，产出“看起来对但缺文件”的补丁。
派单前必须核对基线。

## 8. 失败与重试

| 情况 | 处置 |
|---|---|
| 验收不通过 | 出回修单，重试 ≤ 2 次 |
| 门禁失败 | 先修实现，不得改门禁 |
| worker 失联 | 按 `06-takeover-recovery.md` 判定，不盲目重派 |
| 任务规格有误 | 先修工单，再重派；不得让 worker 猜 |
| 连续失败 | 升级给人，附失败证据与已尝试方案 |
