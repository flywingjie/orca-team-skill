# 06 接管、失联与恢复

> 对应 `SPEC.md` §9。接管是高风险动作：**先证明，再动手**。

## 1. 三类“接管”，不要混为一谈

| 类型 | 对象 | 本质 | 授权条件 |
|---|---|---|---|
| **T-1 终端接管** | 一个已存在、但未被监督的终端 | 把终端纳入调度 | 终端空闲、无其他调度在管、不是移交通道启动 |
| **T-2 Run 接管** | 原协调者失联的 Run | 取得编排所有权 | 原协调者确认失联、无健康活跃 worker、证据已记录 |
| **T-3 续派** | 已结算的 worker | 重新唤醒，保留上下文 | 正常结算后需要追加工作 |

## 2. T-1 终端接管

### 2.1 适用

- 你手动起了一个 agent 终端，想把它纳入监督（拿 `worker_done`、收消息、可结算）。
- 或 C 类 agent（pi 等）需要自定义模型 argv，先起终端再接管。

### 2.2 命令形态

```text
worker-start --task <task_id> --terminal <handle> --worktree <existing-worktree> --agent <id>
```

### 2.3 硬约束

1. **不能与 `--model` 同用**：模型已由终端启动命令决定。
2. **既有工作区不接受建树参数**：`--name` / `--repo` / `--base-branch` / `--setup` 只对新建工作区有效。
3. **移交通道启动的终端不能被接管**：移交（handoff）在启动时写入生命周期权威，
   事后收编会导致两个 agent 在同一工作区互相踩。必须先关闭无监督那只，再按受监督通道重起。
4. **已结算 worker 的终端**：在自动释放时间点之前接管会取消自动释放；过了时间点会被拒绝，
   等释放完成再试。
5. **用户保持打开的终端**：接管后仍保持打开，不会被自动关闭。

### 2.4 接管后

- 补发工单正文（如果接管前没有投递）。
- 读取已有输出，确认它当前在做什么。
- 更新工作区状态行。

## 3. T-2 Run 接管（原协调者失联）

### 3.1 前置条件（全部满足）

1. 原协调者进程已退出，或终端已关闭，**无法继续证明所有权**；
2. 该 Run 没有健康的活跃 worker（用 worker 列表/状态确认）；
3. 已收集证据：原协调者标识、失联时间、最后状态、未结算任务清单；
4. 已确认没有第二个活跃协调者。

### 3.2 命令形态

```text
run-use --id <run_id> --takeover-legacy
check --run <run_id>
```

### 3.3 禁止

- 原协调者仍活跃时接管；
- 因“等太久”“没回复”“看起来卡了”就接管；
- 同时保留两个协调者；
- 接管后从头重跑已完成任务。

### 3.4 接管后

1. 读 `task-list` 与 `worker-list`，确认哪些任务已结算、哪些未结算。
2. 对未结算任务读已有输出与补丁，判断能否续跑。
3. 记录接管：原因、原协调者、接管人、时间、当前状态。
4. 更新状态行与 Runbook。

## 4. T-3 续派（已结算 worker）

优先用消息通道，而不是重新起一个：

```text
send --to dispatch:<dispatch_id> --subject "<主题>" --body "<追加工作>"
```

- 工作中：在当前回合结束后收到；
- 已结束/已关闭：作为后续 Task 重新唤醒，并重新结算；
- 回执会说明是哪种情况。

**禁止**：绕过调度直接向受监督 worker 的终端注入指令；那会绕过结算与消息追踪。

## 5. 停止、围栏与释放

| 动作 | 命令形态 | 语义 | 何时用 |
|---|---|---|---|
| 围栏并停止 | `worker-stop --dispatch <id>` | 停止 agent 终端 | 明确取消 |
| 围栏但不声称已停 | `worker-abandon --dispatch <id>` | 进程状态未知，不谎报 | 无法确认进程是否退出 |
| 释放终端 | `worker-release --dispatch <id>` | 结算后回收资源 | 不再需要该 worker |
| 保持打开 | `worker-keep-open --dispatch <id>` | 结算后保留 | 用户还要继续对话 |
| 关闭终端 | `terminal close --terminal <handle>` | 关闭单个终端 | 清理移交通道/残留 |

**纪律**：进程状态未知时只能“围栏 + 标注未知”，不得报告“已退出”。

## 6. 失败分类

| 现象 | 判定 | 处置 |
|---|---|---|
| 输出含 `429` / `rate_limit` | **限流**，不是卡死 | 等配额恢复；`send` 续跑；不要重启 |
| 屏幕两帧逐字节相同 + 计数器冻结 + 终端空闲 | **停滞** | 先读屏幕找错误；能续跑就续跑 |
| 进程退出 / 终端关闭 | **崩溃** | 读最后输出；修因；用 `--retry-of` 重派 |
| 状态 `outcome_unknown` | **未知** | 读 `worker-show` / `worker-read`；不要盲目重派 |
| `worker_done` 明确失败 | **失败** | 按失败处置；不得标记完成 |
| 长时间无消息但进程活着 | **检查点**，不是失败 | 继续等；定期核对所有在跑任务 |

**判定三证**（停滞）：屏幕两帧逐字节相同 + 计数器冻结 + 终端空闲等待超时。
缺一不可；只有“没消息”不能判停滞。

## 7. 恢复顺序

```text
① 读证据：worker-show / worker-read / 终端屏幕 / 已有补丁
② 分类：限流 / 停滞 / 崩溃 / 未知 / 失败
③ 选择：
   ├─ 限流 → 等待 + send 续跑，不重启
   ├─ 停滞 → 读错误；能续跑则 send；否则 stop 后重派
   ├─ 崩溃 → 修因 + --retry-of 重派
   └─ 未知 → 补齐证据再判；不得凭猜测接管
④ 记录：原因、动作、结果、剩余风险
⑤ 更新状态行与分配表
```

## 8. 接管的禁止清单

- 不接管仍在健康运行、属于别人的 worker/Run。
- 不接管移交通道启动的终端。
- 不在同一工作区同时挂两个写同一文件的受监督 worker。
- 不通过终端注入“遥控”受监督 worker。
- 不因超时、沉默、不可验证就判定失败或接管。
- 不在接管后丢弃原 worker 的已有产出。
- 不在未记录证据的情况下接管。

## 9. 接管记录模板

```text
接管类型：T-1 / T-2 / T-3
接管对象：<handle / run_id / dispatch_id>
原执行者：<标识 / 最后已知状态>
接管原因：<限流 / 崩溃 / 失联 / 正常续派>
证据：<worker-read 摘要 / 终端截图 / 进程状态 / 时间>
已做动作：<stop / send / release / record>
当前状态：<在跑 / 已结算 / 未知>
剩余风险：<...>
接管人：<标识>    时间：<ISO8601>
```
