# 03 工单五段式

> 对应 `SPEC.md` §6。工单是派单的最小单位，也是验收的唯一依据。

## 1. 什么是一张合格的工单

一张合格的工单满足：

1. **自足**：单独交给一个新 agent，它不需要问任何问题就能开工。
2. **可判定**：每条改动都能被“看到了 / 没看到”判定。
3. **有边界**：明确列出不碰的文件，越界即停。
4. **可验收**：命令 + 期望结果成对出现。
5. **无工具**：不出现任何具体 CLI 的派单命令。

### 1.1 「可独立验收」的机械判据

拆单时判定一批触点能不能放进同一张单，逐条核对（缺一不可）：

| # | 判据 | 判定方法 | 不满足时 |
|---|---|---|---|
| 1 | **单一验收动作** | 存在一组命令能一次性判定这批触点对错，不依赖别的单的产物 | 拆开 |
| 2 | **单一 owner** | 这批触点涉及的层只有一个 owner（契约定义层 / 契约产物层 / 共享底座各有其主，见 `SPEC.md` P-1、P-2） | 回流对应 owner，或拆开 |
| 3 | **单一基线** | 这批触点在同一基线上可独立比对 | 拆开 |

对照口径：`SPEC.md` `L-4`。**「多文件」不等于「多张单」**；两张单绝不能碰同一文件。

## 2. 模板

```markdown
# 工单 <单号>：<一句话标题>

## 目标

<本单要解决什么问题；精确到目录/文件；列出“不碰”的相邻文件>

## 改动

1. <可核对的结果 1>
2. <可核对的结果 2>
3. <测试 / 迁移 / 文档等附带产出>

## 约束

- 口径：<引用规格条款 / 决策编号 / 既有实现>
- 禁改：<逐个点名的文件或目录>
- 契约：<契约定义/产物是否归本单；默认否>
- 迁移号：<本单占用的号段；无则写“无”>
- 基线：<origin/main 或集成分支>
- 越界处置：需要改范围外文件 / 改契约 / commit / push / 合并时，停下上报
- 歧义处置：业务歧义停下上报；实现歧义自行决定并在回报中写明

## 归属

- 本单独占文件：
  - <path/1>
  - <path/2>
- 依赖：<上游单号, 上游单号>（无则写「无」）
- 与他单相邻：<相邻单号 + 交接点>
- 分支：feature/<单号>-<短名>
- 补丁包路径：patches/<单号>/<worker>/

## 验收

| # | 命令 | 期望结果 |
|---|---|---|
| 1 | `<command>` | <期望输出 / 退出码> |
| 2 | `<command>` | <期望输出 / 退出码> |

负路径覆盖：
- [ ] 无权限
- [ ] 无效输入
- [ ] 重复提交
- [ ] 并发冲突
- [ ] 超时 / 部分失败
```

## 3. 逐段填写要点

### 3.1 目标

必须出现具体路径。反例：

- ❌ “做整个模块”
- ❌ “优化一下接口”
- ✅ “在 `server/api/orders.py` 增加分页参数，并保持 `GET /orders` 向后兼容；不碰 `server/models/`”

### 3.2 改动

每条都要能被“看到了 / 没看到”判定。反例：

- ❌ “完善错误处理”
- ✅ “无效 `page` 返回 400，错误码 `INVALID_PAGE`；补一条负路径测试”

### 3.3 约束

约束段是防冲突的唯一有效手段。至少包含：

- 1 个口径来源；
- 1 个禁改文件；
- 1 条越界处置；
- 1 条歧义处置。

### 3.4 归属

- 独占文件必须逐个列出，不能写“相关文件”。
- **依赖必须写明**：「依赖」行列出上游单号；无依赖写「无」。依赖是排波次与一致性校验的唯一依据，
  不得只存在于编排配置里（`SPEC.md` `K-7`）。
- 与他单相邻时，写明交接点（谁先改、谁后改、改完通知谁）。
- 分支名与单号绑定，便于事后对账。

### 3.5 验收

- 命令必须可复制执行。
- 期望结果必须是可判定的（输出片段、退出码、文件存在）。
- 负路径按风险选择，不要求每次全覆盖，但必须写明覆盖了哪几条。

### 3.6 口径引用格式（`SPEC.md` `K-6`）

「约束」段的口径来源**必须带命名空间**：

| 写法 | 指向 | 示例 |
|---|---|---|
| `ots:<条目号>` | 本规范的条款 | `ots:R-7`（业务政策由 R-1 决定） |
| `spec:<仓内路径>#<锚点>` | 项目规格文件 | `spec:specs/orders/spec.md#3.2` |
| `dec:<决策编号>` | 决策记录 | `dec:D-014` |

裸编号（`R-7`、`3.2`）**不合规**：worker 无法判断该查哪个文件，也容易与项目自身编号混淆。

> 引用是否指向真实条目目前靠人读核对，尚未工具化；工单↔编排配置的一致性由
> `scripts/check_consistency.py` 负责（见 `scripts/README.md`）。

## 4. 派单正文 = 角色卡 + 工单 + 纪律尾巴

投喂给 worker 的正文必须三段齐全：

```markdown
# 角色卡
<角色卡全文>

# 本次任务
<工单五段式全文>

# 纪律
- 已确认决策不得推翻，已拒绝方案不得重提；有疑问上报。
- 只改「归属」段点名的文件；需要越界时停下上报。
- 不 commit / push / 合并；破坏性 git 命令全禁。
- 收尾交付补丁包（manifest + change.patch + evidence）。
- 回报三句：做了什么 / 凭什么算做完 / 还有什么没做。
- 失败必须显式写为失败。
```

缺纪律尾巴的 worker 容易“自说自话”，这是实测最常见的偏差来源。

## 5. 单号与命名

推荐格式：

```text
<区域>-<序号>[-<短名>]
例：API-014-pagination
    WEB-021-order-drawer
    DB-007-add-index
```

要求：

- 单号在项目内唯一；
- 分支名包含单号：`feature/<单号>-<短名>`；
- 补丁包路径包含单号：`patches/<单号>/<worker>/`；
- 状态行以单号开头，便于检索。

## 6. 状态行

工作区状态行是跨 agent 的唯一实时通道。格式：

```text
<单号> 完成：<一句话结果>，补丁包 patches/<单号>/
<单号> 阻塞：<阻塞点>，需要 <谁> 决定 <什么>
<单号> 待阅：<需要人看什么>
```

要求：

- 关键节点更新（开工、产出里程碑、阻塞、完成）；
- 不写长篇；一句话能让人接上；
- 阻塞必须写明“需要谁决定什么”。

## 7. 常见反例

| 反例 | 问题 | 修法 |
|---|---|---|
| 目标写“相关模块” | 无法判定越界 | 点名目录/文件 |
| 约束段空着 | worker 必然越界 | 至少 1 禁改 + 1 歧义处置 |
| 归属不写 | 两个 agent 改同一文件 | 逐个列独占文件 |
| 验收写“功能正常” | 不可执行 | 命令 + 期望结果 |
| 工单里写派单命令 | 绑死工具 | 命令移到 adapters |
| 工单要求“顺便优化” | 范围失控 | 拆成独立单 |
| 未写基线 | worker 基于旧代码 | 写 `origin/main` 或集成分支 |
