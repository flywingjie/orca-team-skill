# 01 角色与职责

> 对应 `SPEC.md` §3。角色的名字可以换，边界不能换。

## 1. 角色表

| 角色 | 核心问题 | 产出 | 不得做 |
|---|---|---|---|
| 拍板人 | “这个业务口径对不对？” | 决策、签字、合并授权 | 被 agent 代替 |
| 协调者 | “谁在做什么，做到哪了？” | 工单、分配表、验收记录、集成结果 | 替人定业务政策 |
| 顾问 | “主流怎么做？边界在哪？” | 对照表、边界建议、异常清单 | 改代码、跑命令 |
| 设计 | “做成什么样才算对？” | 规格、契约定义、待拍板清单 | 直接实施 |
| 实现者 | “代码改对了吗？” | 补丁包 + 变更清单 + 证据 | commit / push / 合并 |
| 验收者 | “条款都满足了吗？” | 条款级核验表、缺口与风险 | 代写实现 |

## 2. 阶段责任（RACI）

R = 负责执行，A = 最终负责，C = 需咨询，I = 需知会。

| 阶段 | 拍板人 | 协调者 | 顾问 | 设计 | 实现者 | 验收者 |
|---|---|---|---|---|---|---|
| 立项 | A | R | C | C | I | I |
| 方案 | A | R | R | R | C | C |
| 拆单 | I | A/R | I | C | C | I |
| 并行实施 | I | A | I | C | R | I |
| 收口 | I | A/R | I | C | C | I |
| 验收 | A | R | I | C | C | R |
| 回写 | I | A/R | I | I | I | C |

## 3. 角色卡（Role Card）

每个角色必须有一张角色卡，注入任务正文。角色卡至少包含：

```markdown
# <角色名>

## 身份
<一句话：你是谁、对什么负责>

## 职责
<编号列表，3-6 条>

## 边界
<可做什么 / 不可做什么>

## 交付物
<本角色固定产出>

## 禁止
<最容易越界的行为，逐条点名>
```

角色卡不得写成口号；每条都要能被“看到 / 没看到”判定。
模板见 `templates/role-card.md`。

## 4. 角色冲突

- **顾问之间**：写明分歧点与各自依据，交协调者汇总，由拍板人裁决。
- **设计与实现**：以规格为准；规格缺失由设计补，不由实现者自行发明。
- **实现者之间**：以工单「归属」为准；相邻文件有争议时停下上报，不“顺手改一下”。
- **协调者与拍板人**：协调者不得替拍板人做业务决定；拍板人可推翻协调者的实现决策并留痕。

## 5. 角色数量的最小配置

| 规模 | 最小角色 |
|---|---|
| 单 agent 小改动 | 协调者兼任实现者 + 人验收 |
| 一个功能、前后端并行 | 协调者 + 前端 + 后端 + 人验收 |
| 多域/多模块 | 协调者 + 设计 + 顾问（按需）+ 前端 + 后端 + 测试 + 验收 |

角色可以兼任，但**职责不能合并**：兼任验收者的实现者不得验收自己的代码。

### 5.1 角色 × 载体映射

「角色」是**权责轴**（谁有权决定、谁不能做什么、谁签字）；
「agent 实例」是**物理轴**（同时进行、上下文隔离、文件互踩、视角独立）。
两者正交：**多实例 ≠ 多角色**（5 个并行 worker 全是实现者）；
**多角色 ≠ 多实例**（设计→实现有依赖，可在同一会话连着做）。

| 角色 | 最小独立实例 | 规则 |
|---|---|---|
| 拍板人 R-1 | 0（人） | 不可由 agent 代行（`W-4`） |
| 协调者 R-2 | 1 | 同一时刻一只（`S-2`） |
| 顾问 R-3 | 0~N | 可由协调者兼任（只读）；需要独立视角时才拆实例 |
| 设计 R-4 | 0~1 | 可与协调者同实例（上下文连续更省成本） |
| 实现者 R-5 | 1~N | 每张工单至少 1；同波必须不同实例（worktree 隔离） |
| 验收者 R-6 | **1（强制独立）** | 不得与实现者同一实例，且不得用同一模型实例 |

**兼任禁令的完整口径**：

- 实现者不得验收自己的代码（见本节与 `SPEC.md` `R-6`）；
- **协调者亲自写了实现，就不得验收那一张单**——要么换一个独立实例验收，要么退回设计角色重判；
- 「换一个独立实例」指**新会话**，不是同一会话里再演一遍验收者（同一上下文等于自证）。

### 5.2 什么时候加角色，什么时候加 agent 实例

| 出现的情况 | 加角色 | 加实例 | 理由 |
|---|---|---|---|
| 业务口径不确定 | ✅ 顾问/设计 | 看情况 | 角色隔离够用；需要未被主线污染的视角才拆实例 |
| 前后端并行 | ✅ 实现者 ×2 | ✅ 必需 | 既要权责分离，也要真并行 + 文件隔离 |
| 自己写的代码要复核 | ✅ 验收者 | ✅ 必需 | 独立实例才有独立上下文；同实例换卡 = 自证 |
| 两件事有先后依赖 | ✅ 设计→实现 | ❌ | 有依赖就串行，拆实例只增加传参与状态同步成本 |
| 单纯想「多看一遍」 | ❌ | ❌ | 同一 agent 自查第二遍即可 |
| 单文件小改 | ❌ | ❌ | 协调者兼实现 + 人验收 |

三条判据：

1. **加角色** ← 出现了「不同的禁止项」或「不同的签字权」。
2. **加 agent 实例** ← 出现了「需要同时进行」或「必须互相看不见」。
3. **两者都不加** ← 只是「想让人多看一遍」。

**成本判据**：每个 agent 实例的固定成本（建工作区、投喂上下文、等开工、收证据、验收其产出）
约为它实际工时的 1~3 倍。拆实例必须满足「并行收益 > 隔离成本」。

### 5.3 规模阶梯

```text
L0  单实例单角色     协调者兼实现 + 人验收     触发：≤1 张单、1-2 个文件、无契约变更
    ↓ 出现「需要同时进行」或「必须互相看不见」
L1  多实例同角色     N 个实现者并行             触发：前后端/多模块可并行且文件互不相交
    ↓ 出现「不同的禁止项」或「不同的签字权」
L2  多角色           协调者 + 设计 + 实现 + 验收 触发：有决策分离需求
    ↓ 出现接管/跨工具/自动门需求
L3  编排工具 + 门    Orca Run：暂停点、三关、证据链 触发：见 `references/08-orca-cli.md` §1
```

常见错误是**跳过 L0 直接上 L3**：成本暴涨、上下文割裂，还要额外收拾协调工作。

## 6. 角色与模型的对应

角色不等于模型。一个角色可以由不同 agent/模型承担：

- **协调者**：需要强推理与长上下文，优先选最强可用模型。
- **顾问/设计**：需要领域知识与引用能力。
- **实现者**：需要代码能力与工具调用能力，按前后端分工。
- **验收者**：需要独立视角，不得与实现者使用同一模型实例。

模型分配见 `05-model-assignment.md`。
